# Add an MCP tool

> **Last reviewed:** 2026-11-10.

A new tool is a new capability for both the on-device agent and every connected computer. That is
the point of the design, and it is also why a tool needs to be boring: predictable arguments,
predictable failure, and no way around the guards.

## The four edits

### 1. Implement it in `mcp-server/src/main/kotlin/com/aura/mcp/tools/`

Put it in the file for its group (`GestureTools`, `AppTools`, `BrowserTools`, …) or a new one if it
is a new group. Rules:

- **No `android.*` imports.** Take a port (a `XxxBridge` interface) for anything the device must do,
  so the tool runs against `MockPhone` in the JVM bench.
- **A refusal is a result, not an exception.** Return the reason in the text the model reads, and
  say what to do instead. `CallToolResult(isError = true, …)` is for a tool that genuinely failed.
- **Write the description for the model.** One sentence of what it does, then the constraint it
  must respect. `ToolDescriptionBudgetTest` fails if it grows past the budget.
- **KDoc for humans**, to the `AGENTS.md` standard: first line says what it is, then only the
  labelled parts that apply (`Contract:`, `Fails:`, `Change together:`).

### 2. Classify its scope in `McpToolScopes`

`McpScope.READ` only if it cannot move pixels, change settings, launch anything, or affect what the
user sees. Anything else is `WRITE`. An unclassified tool defaults to `WRITE`, so forgetting fails
closed, but say it explicitly anyway.

If it gestures on the screen, it must also be in `ActionGuard`'s grounding-required set;
`ActionGuardListsTest` fails when a gesture tool is missing.

### 3. Register it in `McpToolCatalog`

Add it to the catalog the server builds. It must be registered **through `scopedTool`** — a tool
registered outside the wrapper is invisible to `ControlLock`, `ActionGuard` and the scope check,
which means it is outside the safety story. Do not hand-register.

Read-only tools are cheap; a tool that can send a message or delete something should also be
considered for `ConfirmDestructiveHook`.

### 4. Make the guards agree

| Ask | If yes |
|---|---|
| Can it change the screen? | Add it to the grounding-required set, and make the result report what changed |
| Can it be destructive? | Route it through `ConfirmDestructiveHook` |
| Does it touch a restricted app? | It already cannot: `RestrictedAppsStore` gates at the service |
| Does the model need to see the result? | Return the observation, or the model will act blind and get a `perceive_first` refusal |

## Tests

1. **A unit test** for the pure part, next to the existing ones. Prefer a test that fails when the
   tool's contract changes, not one that restates the implementation.
2. **A bench scenario** in `bench/` if the tool can be misused. Write the adversarial case: what a
   careless model would try, and what must happen instead. Then run:

```bash
cd aura-android
./gradlew :mcp-server:test
```

The report is at `mcp-server/build/toolbench/report.html`.
